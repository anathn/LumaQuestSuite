# STORY-002-04: Child profile CRUD and in-session child selection

## Overview

Expose `ChildProfile` management to authenticated parents, and formalize "selecting an active child" within a parent's session, per ADR-006: children never hold independent credentials — a child is a sub-resource selected within an authenticated parent session.

## User Story

As a parent, I want to list, create, and select among my children's profiles, so that I can manage my family and switch which child's activity I'm viewing or assigning to, without my child ever needing their own login.

## Acceptance Criteria

### Functional Requirements

- [ ] `GET /api/v1/children` returns all `ChildProfile` rows for the authenticated parent's `family_id` (using the STORY-002-03 tenancy dependency).
- [ ] `POST /api/v1/children` creates a new `ChildProfile` under the authenticated parent's `family_id`; `display_name` is required, `grade_band` optional, `preferences` defaults to `{}`.
- [ ] An "active child" concept exists for the session: either a request-scoped `child_id` parameter validated against the family's children, or a lightweight "select active child" endpoint that stores the choice server-side (pick one approach and document it — do not build both).
- [ ] Every request that selects a child validates that the requested `child_id` belongs to the authenticated `family_id` (reuses the STORY-002-03 pattern) — selecting another family's child ID fails.
- [ ] No endpoint accepts or requires a child-specific credential of any kind.

### Non-Functional Requirements

- [ ] Performance: N/A at this scale.
- [ ] Accessibility: N/A (API-only story).
- [ ] Error handling: creating a child with a missing `display_name` returns a 422 validation error from the Pydantic model, not a 500.

### Key Components

1. **`ChildProfileCreate`/`ChildProfileRead` schemas** - Pydantic v2 models matching the fields from STORY-002-01, with `display_name` validated for length/content.
2. **`get_active_child` dependency** - Takes a `child_id` (path or query param, per chosen approach) and the current `family_id`, and 404s if that child doesn't belong to the family — this becomes the standard way every reading/spelling endpoint resolves "which child."

### Dependencies

- STORY-002-01 (`ChildProfile` model).
- STORY-002-03 (tenancy dependency — this story is the first real consumer beyond the isolation tests).

### Code Structure Suggestions

```python
# apps/api/app/accounts/dependencies.py (addition)
def get_active_child(child_id: str, family_id: str = Depends(get_current_family)) -> ChildProfile:
    child = get_child_by_id(child_id)
    if child is None or str(child.family_id) != family_id:
        raise HTTPException(status_code=404)
    return child
```

## Testing Requirements

### Unit Tests

- Test `ChildProfileCreate` schema rejects a missing/empty `display_name`.
- Test `get_active_child` returns 404 for a `child_id` belonging to a different family.

### Integration Tests

- Test scenario: a parent can create a child and immediately see it in `GET /api/v1/children`.
- Test scenario: a parent cannot select or fetch details for a child ID belonging to another family (extends the STORY-002-03 isolation suite).

### Manual Testing

2. `POST /api/v1/children` with a display name.
3. `GET /api/v1/children` and confirm the new child appears.
4. Attempt to use another family's child ID and confirm rejection.

## Notes & Considerations

- Decide and document the "active child" mechanism (explicit `child_id` per request vs. a stored session preference) before other domain modules start depending on it — Reading Quest's `today`/`session` endpoints will all need a consistent way to resolve "which child."
- Do not add reading/spelling feature flags to `ChildProfile.preferences` in this story — that belongs to whichever epic introduces per-game enablement (see Architecture ADR-008's note that a feature flag/permission model is required).
