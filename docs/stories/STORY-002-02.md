# STORY-002-02: Parent authentication: Argon2 password + magic link, Redis session cookie

## Overview

Implement parent-facing authentication exactly as specified in Architecture §3.2/§5.1: email + password (Argon2id) or a magic link, resulting in an opaque, Redis-backed session referenced by an httpOnly/secure/`SameSite=Lax` cookie — not a JWT.

## User Story

As a parent, I want to sign in with my email and password (or a magic link), so that I get a secure session I can trust, and that the system can revoke immediately if needed.

## Acceptance Criteria

### Functional Requirements

- [ ] A `User` (parent) table: `id`, `email` (unique), `password_hash` (nullable, for magic-link-only accounts), `created_at`. `Family.owner_user_id` references this table (reconcile with STORY-002-01).
- [ ] `POST /api/v1/auth/session` accepts either `{email, password}` or a magic-link token, and on success creates a session.
- [ ] Passwords are hashed with Argon2id (not bcrypt/PBKDF2) at rest; verification uses constant-time comparison via the Argon2 library.
- [ ] Magic link flow: a short-lived, single-use token is generated, delivered via email (email delivery may be stubbed/logged in dev), and redeemed exactly once to create a session.
- [ ] On successful auth, a session record is created in Redis (opaque session ID → `{user_id, family_id, created_at}`), and the response sets an httpOnly, secure, `SameSite=Lax` cookie containing only the opaque session ID.
- [ ] Logout invalidates the Redis session record immediately (server-side revocation, not just cookie clearing).
- [ ] Session has a sliding expiry on activity (Architecture §4.3).

### Non-Functional Requirements

- [ ] Performance: session lookup on each request is a single Redis `GET`.
- [ ] Accessibility: N/A (backend story; login form UI is a separate frontend concern not in this story's scope).
- [ ] Error handling: invalid credentials, expired/used magic links, and rate-limited login attempts all return a generic error (no user enumeration via distinct error messages).

### Key Components

1. **`auth.py`** - Wraps `argon2-cffi` for hashing/verification; generates cryptographically random magic-link tokens (e.g., `secrets.token_urlsafe`), stored in Redis with a short TTL and deleted on redemption (single-use).
2. **`sessions.py`** - Owns the Redis key scheme for sessions (e.g., `session:<opaque_id>`), sliding-TTL refresh logic, and cookie attribute construction (`httponly`, `secure`, `samesite=lax`).
3. **Rate limiting** - Login attempts are rate-limited per IP/email via the Redis rate-limit counters described in Architecture §4.3 (fixed window, short TTL) — coordinate with STORY-003 caching work if that lands first, otherwise implement a minimal counter here.

### Code Structure Suggestions

```python
# apps/api/app/accounts/sessions.py
import secrets
from datetime import timedelta

SESSION_TTL = timedelta(hours=12)

def create_session(redis, user_id: str, family_id: str) -> str:
    session_id = secrets.token_urlsafe(32)
    redis.hset(f"session:{session_id}", mapping={"user_id": user_id, "family_id": family_id})
    redis.expire(f"session:{session_id}", int(SESSION_TTL.total_seconds()))
    return session_id

def revoke_session(redis, session_id: str) -> None:
    redis.delete(f"session:{session_id}")
```

## Notes & Considerations

- Do not implement JWTs anywhere in this flow — Architecture §5.1 explicitly chose opaque Redis sessions specifically so a session can be revoked server-side immediately; a JWT would violate that decision.
- Email delivery for magic links can be a logged/stubbed provider in `dev`, but the interface should be swappable for a real provider without touching this story's core logic.
- Coordinate with STORY-002-05 on where the session-signing/cookie-secret value comes from — it must be injected via secrets, not hardcoded here.
