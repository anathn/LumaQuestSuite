## Overview

This is the single most important story in the platform: implement the shared FastAPI dependency that resolves `family_id` from the session and makes it impossible for any handler to query without it (Architecture §3.2, §5.1). Every later domain story depends on this existing and being enforced.

## User Story

As a family using the product, I want a hard guarantee that no request — however it's constructed — can ever read or write another family's data, so that my child's data stays private.

## Acceptance Criteria

### Functional Requirements

- [ ] A `get_current_family` (or similarly named) FastAPI dependency resolves the session cookie → Redis session → `family_id`, and raises 401 if the session is missing/invalid/expired.
- [ ] A lint/test convention (custom test, not just a code review checklist) fails CI if any router function under a protected path is defined without depending on the tenancy dependency, or if it constructs a raw query missing a `family_id` filter where the model has one.
- [ ] A documented "tenancy-scoped query" pattern (e.g., a base repository/query-builder method) that every domain module is expected to use, so `family_id` filtering isn't hand-rolled differently in each module.
- [ ] `GET /api/v1/children` (from STORY-002-04, whichever lands first — coordinate) is the first real endpoint that exercises this dependency end-to-end.

### Non-Functional Requirements

- [ ] Performance: the dependency does one Redis lookup per request; no N+1 session lookups within a single request.
- [ ] Accessibility: N/A.
- [ ] Error handling: a missing/expired/tampered session cookie returns 401 with no information disclosure about why (don't distinguish "expired" from "invalid" in the response body).

### Key Components

1. **`get_current_family` dependency** - Reads the session cookie, looks up the session in Redis (via STORY-002-02's `sessions.py`), and returns the `family_id` (and `user_id`) or raises `HTTPException(401)`.
2. **Tenancy-scoped repository/query helper** - A small helper (e.g., `scoped_query(session, Model, family_id)`) that every domain module's data-access code calls instead of writing raw `select(Model)` calls, making the `family_id` filter structurally hard to forget.
3. **Isolation test harness** - Creates two families with data, authenticates as family A, and asserts every relevant endpoint returns 404/403 (not family B's data) when addressing family B's resources by ID.

### Code Structure Suggestions

```python
# apps/api/app/accounts/dependencies.py
from fastapi import Depends, HTTPException, Request

def get_current_family(request: Request) -> str:
    session_id = request.cookies.get("session_id")
    if not session_id:
        raise HTTPException(status_code=401)
    session = lookup_session(session_id)  # from sessions.py
    if session is None:
        raise HTTPException(status_code=401)
    return session["family_id"]
```

```python
# apps/api/app/core/tenancy.py
from sqlalchemy import select

def scoped_query(model, family_id: str):
    return select(model).where(model.family_id == family_id)
```

## Testing Requirements

### Unit Tests

- Test `get_current_family` raises 401 for a missing cookie, an unknown session ID, and an expired session.
- Test `scoped_query` always includes the `family_id` predicate for a model that has the column.

### Integration Tests

- Test scenario (the core deliverable): create Family A with a child and Family B with a child; authenticate as Family A; request Family B's child by ID via every protected endpoint that exists at this point — all must fail with 404/403, never return Family B's data.
- Test scenario: a request with no session cookie at all is rejected on every protected route.
- Test scenario: a tampered/forged session ID is rejected.

### Manual Testing

1. Authenticate as two different test families via `curl`.
2. Attempt to fetch the other family's child profile by ID and confirm rejection.
3. Confirm a protected route works correctly for the authenticated family's own data.
