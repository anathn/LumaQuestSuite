## Overview

Create the monorepo layout the architecture specifies (PRD §20 "Suggested shared repository layout") and a Dockerfile for each of the three application containers (`web`, `api`, `worker`), so every later story has somewhere to put code and a way to run it identically on a laptop and in production.

## User Story

As a developer, I want a working monorepo scaffold with buildable container images for the web app, API, and worker, so that I can start implementing domain features against a real, containerized stack from day one.

## Technical Implementation

### Files to Create/Modify

| File | Action | Purpose |
|------|--------|---------|
| `apps/api/Dockerfile` | Create | Python 3.12 + FastAPI + uvicorn image |
| `apps/api/app/main.py` | Create | FastAPI app with a `/healthz` route |
| `apps/api/app/worker.py` | Create | Celery app instance, shared by the worker container |

| `apps/web/package.json`, `apps/web/next.config.js` | Create | Minimal Next.js scaffold |
| `docker-compose.yml` | Create | Base stack: `web`, `api`, `worker` on one network |
| `apps/api/README.md` | Create | Documents dependency manager choice and local run instructions |

### Key Components

1. **`apps/api` FastAPI skeleton** - App factory pattern (`create_app()`), one router mounted at `/healthz`, ready for domain routers to be added in later stories without restructuring.
2. **Shared base image for `api`/`worker`** - Either a multi-stage Dockerfile with a shared builder stage, or two Dockerfiles both `FROM` a common internal base image, to avoid dependency drift between API and worker.
3. **`apps/web` Next.js skeleton** - App Router (or Pages Router — pick one and note it in `apps/web/README.md`), one placeholder route.

### Dependencies

- None — this is the first story.

### Code Structure Suggestions

```python
# apps/api/app/main.py
from fastapi import FastAPI

def create_app() -> FastAPI:
    app = FastAPI(title="LumaQuest API", version="0.1.0")

    @app.get("/healthz")
    def healthz():
        return {"status": "ok"}

    return app

app = create_app()
```

```python
# apps/api/app/worker.py
from celery import Celery

celery_app = Celery("lumaquest")
```

## Testing Requirements

### Unit Tests

- Test that `create_app()` returns an app whose `/healthz` route returns HTTP 200 with `{"status": "ok"}`.

### Integration Tests

- Test scenario: `docker compose up` (api + worker + web) reaches a healthy state and `GET /healthz` on the `api` container returns 200.

### Manual Testing

1. Run `docker build` for each of the three images.
2. Run `docker compose up` and confirm all three containers stay running (no restart loops).
3. Curl the API's `/healthz` route from the host once the proxy exists (STORY-001-03) — until then, verify via `docker compose exec`.

## Notes & Considerations

- Don't add Postgres/Redis/MinIO wiring here — that's STORY-001-02. Keep this story to "the three app containers build and run."
- Pin the Python and Node base image versions explicitly (e.g., `python:3.12-slim`, `node:20-slim`) rather than floating tags, so builds are reproducible (Architecture §6.1 "structurally identical" environments).
- Do not commit a `poetry.lock`/`requirements.txt` with unpinned versions — pin exact versions for reproducible builds.
