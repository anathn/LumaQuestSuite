## Overview

Automate the first half of the deployment pipeline from Architecture §6.3: on every merge to `main`, build the `web`, `api`, and `worker` images, tag them with the commit SHA, and push them to a container registry (GHCR).

## User Story

As a developer, I want every merge to `main` to automatically produce SHA-tagged, pushed container images, so that deploys always reference a known, reproducible artifact instead of a locally-built image.

## Acceptance Criteria

### Functional Requirements

- [ ] CI workflow triggers on push/merge to `main`.
- [ ] Workflow builds `apps/web`, `apps/api`, and `worker` images (worker may reuse the api image per STORY-001-01's shared-base decision).
- [ ] Each image is tagged with the short commit SHA and pushed to GHCR (or the chosen registry), plus a `latest`-style moving tag for convenience only (SHA tag is the one deploys reference).
- [ ] Workflow fails the build (and blocks merge, if branch protection is configured) if any image fails to build.
- [ ] Registry authentication credentials are stored as CI secrets, never committed.

### Non-Functional Requirements

- [ ] Performance: use build caching (registry cache or CI cache) so unrelated changes don't rebuild every layer from scratch.
- [ ] Accessibility: N/A.
- [ ] Error handling: a failed push must fail the workflow visibly, not silently skip.

## Technical Implementation

### Files to Create/Modify

| File | Action | Purpose |
|------|--------|---------|
| `.github/workflows/build-images.yml` | Create | Build/tag/push `web`, `api` images on merge to `main` |
| `infra/deployment/README.md` | Create | Documents the image tagging scheme and how a deploy consumes it |

### Key Components

1. **Build matrix job** - One job per image (`web`, `api`) using `docker/build-push-action` (or equivalent), each tagged `ghcr.io/<org>/<repo>-<image>:<sha>`.
2. **Registry login step** - Uses a CI secret (e.g., `GITHUB_TOKEN` for GHCR) to authenticate before pushing.

### Dependencies

- STORY-001-01 (Dockerfiles must exist to build).

### Code Structure Suggestions

```yaml
# .github/workflows/build-images.yml (excerpt)
name: build-images
on:
  push:
    branches: [main]

jobs:
  build:
    strategy:
      matrix:
        image: [web, api]
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - uses: docker/build-push-action@v5
        with:
          context: apps/${{ matrix.image }}
          push: true
          tags: ghcr.io/${{ github.repository }}-${{ matrix.image }}:${{ github.sha }}
          cache-from: type=registry,ref=ghcr.io/${{ github.repository }}-${{ matrix.image }}:buildcache
          cache-to: type=registry,ref=ghcr.io/${{ github.repository }}-${{ matrix.image }}:buildcache,mode=max
```

## Notes & Considerations

- This story only covers build/tag/push. The deploy step that pulls these images into an environment (`docker compose pull && up -d`, with migrations run first) is a separate concern — see STORY-013-05 for automating that sequencing safely.
- Worker image build can be skipped as a separate matrix entry if STORY-001-01 made it a shared image with `api`; don't build/push the same image twice under two tags for no reason.
