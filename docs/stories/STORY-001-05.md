# STORY-001-05: Per-environment Compose stacks (dev/staging/prod) with isolated secrets

## Overview

Split the single Compose configuration built in STORY-001-01–03 into three environments (`dev`, `staging`, `prod`) that share the same base files and differ only in environment variables, resource limits, and replica counts (Architecture §6.4).

## User Story

As an operator, I want dev, staging, and prod to run from the same Compose definitions with environment-specific overrides, so that "it works in staging" reliably predicts "it works in prod."

## Acceptance Criteria

### Functional Requirements

- [ ] A base `docker-compose.yml` plus `docker-compose.dev.yml`, `docker-compose.staging.yml`, `docker-compose.prod.yml` overrides — no environment forks the base file's service definitions.
- [ ] Each environment has its own `.env.<environment>` (or equivalent) holding environment-specific values; none of these files are committed with real secrets (only `.env.example` is committed).
- [ ] `dev` overrides may run self-hosted STT/LLM containers and relaxed TLS (per Architecture §6.4's "dev may run STT/LLM entirely self-hosted"); `staging`/`prod` can switch either adapter to a hosted provider via configuration only, no code change.
- [ ] Each environment's database, Redis, and MinIO state is isolated — no shared volumes or shared containers across environments.
- [ ] Documented resource limits (CPU/memory) per environment on the `api`/`worker`/`postgres` services, appropriate to §9's cost planning (staging smaller than prod).

### Non-Functional Requirements

- [ ] Performance: N/A beyond documented resource limits.
- [ ] Accessibility: N/A.
- [ ] Error handling: starting the wrong override for an environment (e.g., prod flags with dev secrets) should fail loudly via a required-env-var check, not run in a misconfigured half-state.

## Technical Implementation

### Files to Create/Modify

| File | Action | Purpose |
|------|--------|---------|
| `docker-compose.dev.yml` | Modify/Create | Dev overrides (already partially created in earlier stories) |
| `docker-compose.staging.yml` | Create | Staging overrides: smaller resource limits, hosted or self-hosted adapters per cost |
| `docker-compose.prod.yml` | Create | Prod overrides: full resource limits, ACME TLS, hosted/self-hosted adapters as chosen |
| `.env.example` | Modify | Add any new environment-specific variable names introduced here |
| `infra/deployment/README.md` | Modify | Document how to select an environment (`docker compose -f docker-compose.yml -f docker-compose.<env>.yml up -d`) |

### Key Components

1. **Override file convention** - Each `docker-compose.<env>.yml` only adds `environment:`, `deploy.resources`, and adapter-selection variables — it never redefines a service's image/build context, which stays in the base file.
2. **Environment variable naming convention** - A documented prefix/naming scheme so `SPEECH_PROVIDER=self-hosted|hosted` and `LLM_PROVIDER=self-hosted|hosted` (etc.) are consistent across environments.

### Dependencies

- STORY-001-01, STORY-001-02, STORY-001-03 (base Compose stack must exist to be overridden).

### Code Structure Suggestions

```yaml
# docker-compose.prod.yml (excerpt)
services:
  api:
    deploy:
      resources:
        limits:
          cpus: "1.0"
          memory: 1g
    environment:
      SPEECH_PROVIDER: hosted
      LLM_PROVIDER: hosted
  postgres:
    deploy:
      resources:
        limits:
          cpus: "2.0"
          memory: 2g
```

### Integration Tests

- Test scenario: starting the stack with `docker-compose.dev.yml` succeeds without any staging/prod secret present.
- Test scenario: starting the stack with `docker-compose.prod.yml` but missing a required prod secret fails fast with a clear error, rather than starting in a degraded state.

### Manual Testing

1. Run the full stack locally with the dev override; confirm self-hosted adapters (if configured) work.
2. Dry-run the staging override (`docker compose config -f docker-compose.yml -f docker-compose.staging.yml`) and review the rendered config for correctness.
3. Confirm no `.env.staging`/`.env.prod` file is present in version control (`git status`/`.gitignore` check).
