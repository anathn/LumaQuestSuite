## Overview

Formalize how every real secret (DB credentials, Redis URL if it carries a password, provider API keys, session/cookie signing key) reaches the running containers, per Architecture §5.5: environment variables injected from Docker Compose secrets or an environment file outside version control, distinct per environment.

## User Story

As an operator, I want a single, documented, enforced way secrets get into containers, so that no secret is ever baked into an image or committed to the repository, in any environment.

## Acceptance Criteria

### Functional Requirements

- [ ] Every secret consumed anywhere in the stack (DB password, MinIO keys, session signing key, future provider API keys) is listed in `.env.example` with a placeholder value and a comment on where it's used.
- [ ] `.gitignore` excludes all real `.env*` files except `.env.example`.
- [ ] No Dockerfile in the repo has an `ARG`/`ENV` instruction setting a real secret value; secrets only ever arrive via `docker compose`'s `environment:`/`env_file:`/`secrets:` mechanisms at run time.
- [ ] A repo-level check (CI step or pre-commit hook) scans for common secret patterns (e.g., high-entropy strings, `AKIA`, private key headers) in staged changes and fails the build if one is found.
- [ ] The session/cookie signing key introduced in STORY-002-02 is sourced from this mechanism, not hardcoded, as the first real consumer.

### Non-Functional Requirements

- [ ] Performance: N/A.
- [ ] Accessibility: N/A.
- [ ] Error handling: a container that starts without a required secret env var fails fast with a clear error naming the missing variable (extends the pattern from STORY-001-02's settings validation).

## Technical Implementation

### Files to Create/Modify

| File | Action | Purpose |
|------|--------|---------|
| `.env.example` | Modify | Ensure every secret-bearing variable is listed with a placeholder |
| `.gitignore` | Modify | Exclude real `.env*` files |
| `.github/workflows/secret-scan.yml` | Create | CI step running a secret-scanning tool (e.g., gitleaks) against the diff |
| `infra/deployment/README.md` | Modify | Document the secrets flow per environment (local `.env`, CI secrets, host-level secrets file for staging/prod) |

### Key Components

1. **Secret-scanning CI job** - Runs on every PR, fails on a detected secret pattern, and is separate from the image-build workflow so it also covers non-container files (docs, scripts).
2. **Documented per-environment secrets flow** - Explicitly states: dev uses a local `.env` (gitignored); staging/prod use a secrets file placed on the host by the operator (outside the repo) referenced by `env_file:` in the environment's Compose override.

### Dependencies

- STORY-001-05 (per-environment Compose overrides must exist to reference environment-specific secrets files).
- STORY-002-02 (first concrete secret — the session signing key — to validate the mechanism against).

### Code Structure Suggestions

```yaml
# docker-compose.prod.yml (excerpt)
services:
  api:
    env_file:
      - /etc/lumaquest/prod.env   # lives on the host, outside the repo
```

## Notes & Considerations

- This story is about the *mechanism and enforcement*, not generating or rotating specific secret values for staging/prod — that's an operational task for whoever provisions those environments, done outside version control.
- Revisit this story's scanning tool choice if it produces excessive false positives; the goal is a real safety net, not a check developers learn to ignore.
